# Polynomial Tug: classroom team play

The owner requests 32 students, groups of four, two against two, levels and stronger powers, using tug of war. They confirmed **one device per student**. Existing instruction delegates implementation judgement; build a local emulator-backed pilot and show it without publishing.

One teacher room defaults to eight groups. Each group has Pair A and Pair B, two independent student seats each. Students join with a room code or QR link, select their group and pair, and receive a seat label. Group count may be 1–8 for small demonstrations. Only the teacher who creates the room can start, pause, resume or end it; all configured seats must be filled before starting. A student cannot occupy two seats; refresh reconnects using the same anonymous Firebase identity. No student names are collected.

Each pupil gets four choices. Partners have their own questions. A correct answer waits for the partner; both correct creates exactly one team pull. An incorrect answer opens working and requires a fresh question, without erasing the partner's correct answer. After a pull both pupils acknowledge the feedback before advancing. There is no speed bonus or player elimination.

Pairs start at level 1. Every three completed pair pulls raises their level, capped at 4: collect like terms (power 1), subtract brackets (power 2), expand (power 3), mixed polynomials (power 4). Power means rope units per completed cooperative pull. The rope starts at 0 and wins at −24/+24. Levels reset per match. The teacher may end an unfinished match; the current rope position determines its result, with 0 a draw. A paused match accepts no answers. Other groups continue when one finishes.

Teacher screen: code/QR, occupied seats, start/pause/resume/end, eight live ropes, levels and readiness per pair. Student screen: group/pair/seat, both partners' status, live rope, current level/power, one question and large choices, feedback/retry/next. Use existing English copy, school palette, KaTeX and original SVG tug artwork. Preserve the individual Quest and textbook pages; add a Class tug of war link.

Architecture: separate private `polynomialTugRooms` documents, one match document per group and one membership document per authenticated UID. All requests go through authenticated Node routes. Teacher authority comes from the existing teacher check and ownership. Transactions validate room status, membership, question ID and answer index, regenerate answers on the server, and award each pair pull once. Do not send seeds, answer keys, unseen working, other students' questions or internal UIDs. Existing default-deny Firestore rules keep this collection private; no client database reads/writes or rule changes are needed. Poll authenticated state about every two seconds, stop when hidden, and reject stale client responses by revision.

Reuse the verified polynomial question/choice engines and existing Firebase auth/QR tools. Keep game mutations in separate group documents to avoid one class-wide answer-write hotspot. No new dependency. Emulator project `demo-lskc-maths` only. This local URL is for same-computer testing; actual student phones need a separately approved hosted release.

Review refinement: each match also holds a private 256-bit secret. Public question IDs and option-order seeds are separate HMAC outputs. Knowing the public ID cannot reproduce the correct answer's shuffled position. Neither the secret nor its option-order seed appears in any public view.
